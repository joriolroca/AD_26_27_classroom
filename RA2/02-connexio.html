1. L'URL JDBC

Per connectar-se, el DriverManager necessita saber quin driver fer servir i on és la base de dades. Tot això va dins de l'URL JDBC:

Text Text 
jdbc:<subprotocol>:<identificador de la base de dades>
  • jdbc és fix.
  • El subprotocol identifica el driver (postgresql, h2, mysql...).
  • La resta depèn de cada driver: normalment màquina, port i nom de la base de dades, i opcionalment paràmetres.
SGBDExemple d'URL
PostgreSQLjdbc:postgresql://localhost:5432/botiga
H2 (fitxer)jdbc:h2:./dades/botiga
H2 (memòria)jdbc:h2:mem:botiga
MySQLjdbc:mysql://localhost:3306/botiga
MariaDBjdbc:mariadb://localhost:3306/botiga
Oraclejdbc:oracle:thin:@//localhost:1521/XEPDB1
SQL Serverjdbc:sqlserver://localhost:1433;databaseName=botiga
SQLitejdbc:sqlite:botiga.db

Els paràmetres addicionals s'afegeixen amb una sintaxi que també depèn del driver:

Text Text 
jdbc:postgresql://localhost:5432/botiga?ApplicationName=botiga&connectTimeout=5

Compte

l'usuari i la contrasenya es poden posar a l'URL, però no és recomanable. Es passen com a paràmetres separats de getConnection, o millor encara, des d'un fitxer de configuració (apartat 3).

2. Obrir una connexió

La classe DriverManager té tres versions de getConnection:

Java Java 
Connection c1 = DriverManager.getConnection(url);                       // sense credencials (H2 en memòria)
Connection c2 = DriverManager.getConnection(url, usuari, contrasenya);  // la més habitual
Connection c3 = DriverManager.getConnection(url, propietats);           // amb un objecte Properties

Un objecte Connection representa una sessió oberta amb el SGBD. Mentre està oberta ocupa recursos al client i, sobretot, al servidor: un procés, memòria i una de les connexions permeses (PostgreSQL n'accepta 100 per defecte).

Java Java 
String URL = "jdbc:postgresql://localhost:5432/postgres";
String USER = "postgres";
String PASS = "1234";

try (Connection con = DriverManager.getConnection(URL, USER, PASS)) {
    System.out.println("Connectat a " + con.getMetaData().getDatabaseProductName());
} catch (SQLException e) {
    System.err.println("Error de connexió: " + e.getMessage());
}

3. Configuració fora del codi

Escriure l'URL i la contrasenya dins del codi té dos problemes: per canviar de base de dades cal recompilar, i la contrasenya acaba al repositori de codi.

La solució és un fitxer de propietats, conn.properties, dins de la carpeta src/main/resources del projecte:

Text Text 
simplebanc/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── ...
        └── resources/
            └── conn.properties

Un fitxer .properties és un fitxer de text amb una propietat per cada línia, en format clau=valor. Les línies que comencen per # són comentaris:

conn.properties Properties 
# Gestor independent: PostgreSQL al contenidor Docker
db.url=jdbc:postgresql://localhost:5432/Iticbanc
db.usuari=M06ACTRA2
db.contrasenya=ssshhh..itsasecret!

Java llegeix aquests fitxers amb la classe Properties. El mètode load() rep un lector, llegeix totes les línies i guarda cada parella clau-valor. Després, getProperty("clau") retorna el valor:

Java Java 
Properties p = new Properties();
p.load(Files.newBufferedReader(Path.of("src", "main", "resources", "conn.properties")));

String url = p.getProperty("db.url");        // "jdbc:postgresql://localhost:5432/Iticbanc"

Amb això ja es pot escriure una classe que centralitza l'obtenció de connexions. Totes les unitats següents la faran servir:

ConnexioBD.java Java 
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.util.Properties;

public final class ConnexioBD {

    private static final Path FITXER_CONFIG =
            Path.of("src", "main", "resources", "conn.properties");

    private static final Properties CONFIG = carregarConfiguracio();

    private ConnexioBD() {
        // Classe d'utilitat: no s'instancia
    }

    private static Properties carregarConfiguracio() {
        Properties p = new Properties();
        // El lector es declara al try-with-resources perquè es tanqui sol
        try (BufferedReader lector = Files.newBufferedReader(FITXER_CONFIG)) {
            p.load(lector);
        } catch (IOException e) {
            throw new IllegalStateException("No s'ha pogut llegir " + FITXER_CONFIG.toAbsolutePath(), e);
        }
        return p;
    }

    /** Retorna una connexió nova. Qui la demana és responsable de tancar-la. */
    public static Connection obtenir() throws SQLException {
        return DriverManager.getConnection(
                CONFIG.getProperty("db.url"),
                CONFIG.getProperty("db.usuari"),
                CONFIG.getProperty("db.contrasenya"));
    }
}

Ús:

Java Java 
try (Connection con = ConnexioBD.obtenir()) {
    System.out.println("Connectat a " + con.getMetaData().getURL());
}

Nota

Files.newBufferedReader llegeix el fitxer en UTF-8, de manera que els valors poden contenir accents sense problemes.

Compte

en un projecte real, conn.properties amb credencials de producció no es puja mai al repositori: s'afegeix al .gitignore i es distribueix un conn.properties.exemple sense contrasenyes.

4. Tancar els recursos

Connection, Statement, PreparedStatement, CallableStatement i ResultSet ocupen recursos al client i al servidor. S'han de tancar sempre quan s'acaben de fer servir, tant si l'operació ha anat bé com si ha fallat.

Si no es tanquen, el programa acumula connexions obertes (connection leak) fins que el servidor arriba al límit i rebutja les noves amb l'error too many clients already.

5. Errors de connexió: SQLException

Gairebé tots els mètodes de JDBC declaren throws SQLException, que és una excepció comprovada (checked). A més del missatge, porta dos codis útils:

MètodeRetornaExemple
getMessage()Descripció de l'error, del driverConnection to localhost:5432 refused
getSQLState()Codi estàndard de 5 caràcters (SQL:2003)08001
getErrorCode()Codi propi del fabricant0 a PostgreSQL, varia a cada SGBD

6. Pool de connexions

Obrir una connexió és lent: cal establir la connexió TCP, autenticar-se i crear la sessió al servidor. Per a un programa que fa poques operacions no importa, però una aplicació que atén centenars de peticions per segon no es pot permetre obrir i tancar una connexió per a cadascuna.

Definició

Un pool de connexions és un conjunt de connexions que es creen per endavant i es reutilitzen. Quan l'aplicació en demana una, el pool en presta una de lliure; quan l'aplicació la "tanca", en realitat la retorna al pool, oberta i a punt per a la petició següent.

A JDBC, el pool s'obté a través de la interfície javax.sql.DataSource, que té un mètode getConnection(). El codi que fa servir la connexió no canvia: continua cridant close() dins del try-with-resources.

La biblioteca de pool més utilitzada a Java és HikariCP. Com a exemple, l'únic canvi seria a ConnexioBD:

pom.xml (fragment) XML 
<dependency>
    <groupId>com.zaxxer</groupId>
    <artifactId>HikariCP</artifactId>
    <version>5.1.0</version>
</dependency>
Java Java 
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import com.zaxxer.hikari.pool.HikariPool.PoolInitializationException;

// Es crea una sola vegada, en arrencar l'aplicació
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:postgresql://localhost:5432/botiga");
config.setUsername("dam");
config.setPassword("dam");
config.setMaximumPoolSize(10);            // com a molt 10 connexions obertes alhora

try (HikariDataSource pool = new HikariDataSource(config)) {
    // A cada operació:
    try (Connection con = pool.getConnection()) {   // presta una connexió del pool
        // ...
    }                                               // close() la retorna al pool
} catch (PoolInitializationException e) {           // el pool no ha pogut arrencar
    System.out.println("No s'ha pogut connectar a la base de dades: " + e.getMessage());
} catch (SQLException e) {                          // error en una operació
    System.out.println("Error de base de dades: " + e.getMessage());
}
