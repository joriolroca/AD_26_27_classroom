Gestió de les excepcions

Per què un programa no s'ha d'aturar de cop davant d'un error: com Java distingeix les excepcions checked de les unchecked, els blocs try-catch-finally, el try-with-resources, i quan cal llançar (throw) o declarar (throws) una excepció pròpia.

DAM RA1 Excepcions

Criteris d'avaluació relacionats

  • 1.6 Preveu i gestiona les excepcions.

Què aprendràs

En acabar aquesta unitat has de ser capaç de:

  • Explicar què és una excepció i per què el llenguatge Java en necessita un mecanisme.
  • Distingir les excepcions comprovades (checked) de les no comprovades (unchecked) i situar-les a la jerarquia de Throwable.
  • Escriure blocs try-catch-finally correctament i saber què s'executa i quan.
  • Utilitzar try-with-resources per tancar recursos de forma segura.
  • Diferenciar throw de throws i saber quan cal fer servir cadascun.
  • Crear excepcions pròpies quan les que ofereix Java no expressen prou bé l'error.
  • Aplicar bones pràctiques en el tractament d'errors.

1. Què són les excepcions?

Definició

Les excepcions són els mitjans que ofereixen els llenguatges de programació per tractar situacions anòmales que poden succeir durant l'execució d'un programa, donant lloc a la interrupció del flux normal que aquest programa té.

Un exemple clàssic de situació anòmala és la divisió d'un nombre per zero. Però no és l'única: d'altres ben conegudes són intentar obrir un fitxer que no existeix o quedar-nos sense memòria a la JVM quan un programa ha entrat en una mena de bucle infinit.

La forma amb la qual s'aborda una excepció (per exemple, aturar l'execució i llançar un missatge) és el que d'ara endavant anomenarem gestió de les excepcions.

Mira aquest programa:

MainDiv.java Java 
public class MainDiv {

    public static int exactdivision (int dividend, int divisor) {

        int c = dividend / divisor;

        return c;
    }

    public static void main (String args[]) {

        int a = 10;
        int b = 0;

        int result = exactdivision(a, b);

        System.out.println("El resultat de la divisió d'"+ a +
        " entre " + b + " és: "+ result);

    }
}

En executar-lo, el programa es tanca de cop, no mostra el missatge del codi: "El resultat de la divisió..." i en canvi la consola mostra:

Consola 
Exception in thread "main" java.lang.ArithmeticException: /
by zero at MainDiv.Exactdivision(MainDiv.java:5)
        at MainDiv.main(MainDiv.java:15)

Això és una excepció: un esdeveniment anòmal que es produeix durant l'execució i que trenca el flux normal de les instruccions.

No confondre amb errors de compilació

Tipus de problemaEn quin momentQui avisaExemple
Error de sintaxi o de tipus En temps de compilació El compilador, abans d'executar el programa int x = "hola";
Excepció En temps d'execució La JVM, mentre el programa s'està executant Dividir per zero, fitxer inexistent, índex fora de rang

2. Per a què serveixen?

Les excepcions són de vital importància en el disseny i la implementació de qualsevol codi, per tal que el programa es pugui anticipar i controlar davant de qualsevol situació anòmala.

La gestió d'excepcions serveix per separar el codi del programa del codi que gestionarà els possibles errors, donant l'oportunitat de reaccionar en comptes de deixar que el programa mori.

Dues raons per les quals serveixen les excepcions

  • Alertar-nos de les situacions anòmales que es poden donar en el nostre codi.
  • Permetre'ns decidir com ha de respondre el codi davant d'aquestes situacions.

3. Checked vs. Unchecked

Java distingeix dos grans tipus de situacions anòmales:

Checked (comprovades)Unchecked (no comprovades)
Representen Situacions externes, previsibles i de les quals et pots recuperar (fitxer no existeix, l'usuari no té permisos, problemes de connexió a la base de dades...) Errors de programació (accedir a un índex invàlid, dividir per zero, un null no comprovat, convertir a número un text que no ho és)
Gestionar les excepcions El compilador t'obliga a capturar-les No és obligatori, és responsabilitat del programador
Exemple IOException, SQLException NullPointerException, ArithmeticException, NumberFormatException

Regla pràctica

Si l'error és culpa de l'entorn (el fitxer no hi és, no hi ha xarxa), sol ser checked. Si l'error és culpa del codi (no vas comprovar una condició abans d'usar una variable), sol ser unchecked.

5. Com les utilitzem: try-catch

La sintaxi bàsica és:

Sintaxi Java 
try {
    // codi del programa (pot llançar una excepció)
} catch (TipusExcepcio nomVariable) {
    // codi que s'executa NOMÉS si s'ha produït una excepció
}

5.1 Exemple bàsic

Si agafem de referència el codi del principi i gestionem les excepcions de forma genèrica:

MainDiv.java Java 
public class MainDiv {

    public static int exactdivision (int dividend, int divisor) {

        int c = dividend / divisor;

        return c;
    }

    public static void main (String args[]) {

        int a = 10;
        int b = 0;

        try{
            //Codi on s'executa el programa. Si hi ha algun error es controla en el catch
            int result = exactdivision(a, b);

            System.out.println("El resultat de la divisió d'"+ a +
            " entre " + b + " és: "+ result);
        }
        catch(Exception ex){
            //Si dins del codi del try hi ha un error es captura en aquest codi
            System.out.println("CATCH: Hi ha hagut un error inesperat: " + ex.getMessage());
        }

    }
}

En aquest cas el programa no es tanca de forma inesperada i mostra el missatge que hem indicat en el catch:

Consola 
CATCH: Hi ha hagut un error inesperat: / by zero

5.2 Múltiples catch

Un try pot anar seguit de diversos catch, un per cada tipus d'error que vulguis tractar de forma diferent. L'ordre importa: de més específic a més general.

Exemple.java Java 
try {
    int[] notes = {5, 7, 9};
    int index = Integer.parseInt(args[0]);
    System.out.println(notes[index]);

} catch (NumberFormatException e) {
    System.out.println("L'argument no és un número.");
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Aquest índex no existeix a l'array.");
} catch (Exception e) {
    System.out.println("Ha passat un error inesperat: " + e.getMessage());
}

Si poses catch (Exception e) abans dels altres, el compilador dona error: com Exception és la superclasse de totes dues, mai s'arribaria a executar la resta de blocs catch, que quedarien codi mort.

5.3 Multi-catch (|)

Quan vols tractar dos tipus d'excepció exactament de la mateixa manera, pots agrupar-los amb | en un sol catch:

Exemple.java Java 
try {
    processarFitxer("dades.csv");
} catch (FileNotFoundException | NumberFormatException e) {
    System.out.println("No s'ha pogut processar el fitxer: " + e.getMessage());
}

6. Finally

El bloc finally és una part opcional que pots afegir després d'un try (i dels seus catch)

La seva característica principal és que sempre s'executa, tant si hi ha una excepció com si no, i fins i tot si dins del try hi ha un return.

Serveix per posar-hi codi de "neteja" que ha de passar sí o sí: tancar una connexió a la base de dades, tancar un fitxer, alliberar recursos, ...

Diferències entre try, catch i finally

BlocQuan s'executaPer a què serveix
try Sempre s'intenta; s'atura al primer punt on salti una excepció Conté el codi "normal", el que pot fallar
catch Només si el try ha llançat una excepció del tipus indicat (o subtipus) Conté la reacció davant de l'error
finally Sempre, hi hagi hagut excepció o no, i encara que el try o el catch continguin un return Conté el codi de neteja: tancar fitxers, connexions, alliberar recursos

6.1 Exemple complet

MainDiv.java Java 
public class MainDiv {

    public static int exactdivision (int dividend, int divisor) {

        int c = dividend / divisor;

        return c;
    }

    public static void main (String args[]) {

        int a = 10;
        int b = 0;

        try{
            int result = exactdivision(a, b);

            System.out.println("El resultat de la divisió d'"+ a +
            " entre " + b + " és: "+ result);
        }
        catch(Exception ex){
            //Si dins del codi del try hi ha un error es captura en aquest codi
            System.out.println("CATCH: Hi ha hagut un error inesperat: " + ex.getMessage());
        }
        finally {
            System.out.println("FINALLY: Aquest missatge es mostra sempre, hi hagi error o no.");
        }

    }
}

En aquest cas el programa mostra:

6.2 El finally s'executa fins i tot amb un return

Exemple.java Java 
public static int prova() {
    try {
        System.out.println("dins del try");
        return 1;
    } finally {
        System.out.println("dins del finally"); // s'imprimeix ABANS de retornar
    }
}
// Sortida: "dins del try" -> "dins del finally" -> el mètode retorna 1
Consola 
dins del try
dins del finally
//el mètode retorna 1.

El finally gairebé sempre s'executa

El finally només es pot saltar si la JVM es tanca de cop (System.exit(), un tall de corrent, un Error molt greu com un StackOverflowError irrecuperable...). A efectes pràctics, dona per fet que sempre s'executa.

7. Try-with-resources

Tancar recursos "a mà" dins d'un finally (com a l'exemple que veuràs a continuació) és farragós i propens a errors. Des de Java 7 existeix el try-with-resources, pensat per a qualsevol classe que implementi la interfície AutoCloseable (com FileReader, BufferedReader, una connexió a base de dades, etc.).

Exemple.java Java 
try (FileReader fr = new FileReader("notes.txt");
     BufferedReader br = new BufferedReader(fr)) {

    String linia;
    while ((linia = br.readLine()) != null) {
        System.out.println(linia);
    }

} catch (IOException e) {
    System.out.println("Error llegint el fitxer: " + e.getMessage());
}
// fr i br es tanquen AUTOMÀTICAMENT en sortir del try, en ordre invers al que es van obrir,
// sense necessitat d'escriure cap finally.

Amb el finally es faria de la següent forma:

Exemple.java Java 
FileReader fr = null;
BufferedReader br = null;

try {
    fr = new FileReader("notes.txt");
    br = new BufferedReader(fr);

    String linia;
    while ((linia = br.readLine()) != null) {
        System.out.println(linia);
    }
} catch (IOException e) {
    System.out.println("Error llegint el fitxer: " + e.getMessage());
} finally {
    // close() també pot llançar IOException: cal un altre try-catch dins del finally
    try {
        if (br != null) br.close();   // tancar el BufferedReader tanca també el FileReader
        else if (fr != null) fr.close();
    } catch (IOException e) {
        System.out.println("Error tancant el fitxer: " + e.getMessage());
    }
}

Avantatges respecte a fer-ho amb finally

  • No cal recordar-se de tancar el recurs: es tanca sempre, encara que salti una excepció.
  • El codi és més curt i llegible.
  • Si es tanquen diversos recursos, es tanquen en l'ordre correcte automàticament.

8. El throw: llançar una excepció

Fins ara hem capturat excepcions que llançava Java directament. Però també podem llançar-ne nosaltres, quan detectem que una dada no compleix una regla del nostre programa.

Alumne.java Java 
public class Alumne {
    private String nom;
    private int nota;

    public void setNota(int nota) {
        if (nota < 0 || nota > 10) {
            throw new IllegalArgumentException("La nota ha d'estar entre 0 i 10, rebut: " + nota);
        }
        this.nota = nota;
    }
}
Main.java Java 
Alumne a = new Alumne();
a.setNota(15); // llança IllegalArgumentException i el programa s'atura aquí (si ningú la captura)

throw és una instrucció: crea (amb new) un objecte excepció i el llança en aquell mateix instant. Serveix per a:

  • Validar dades d'entrada: paràmetres d'un mètode, dades llegides de l'usuari o d'un fitxer.
  • Protegir l'estat intern d'un objecte (evitar que quedi en un estat invàlid).
  • Avisar qui ha cridat el mètode que alguna cosa no es pot completar, en comptes de retornar un valor "estrany" com -1 o null que passaria desapercebut.

Un cop llançada, l'excepció es comporta exactament igual que si l'hagués llançat Java: puja pels mètodes que han fet la crida fins que algú la captura amb catch, o el programa acaba si ningú ho fa.

9. El throws: declarar excepcions al mètode

throws (amb "s") és molt diferent de throw: no llança res, només avisa. Es fa servir a la capçalera d'un mètode per declarar que aquest mètode pot llançar una excepció checked i que qui el cridi n'haurà de fer-se càrrec.

LectorFitxer.java Java 
import java.io.FileReader;
import java.io.IOException;

public class LectorFitxer {

    // Aquest mètode NO captura l'excepció: l'ha de gestionar qui el cridi
    public static void llegir(String nomFitxer) throws IOException {
        FileReader fr = new FileReader(nomFitxer); // pot llançar FileNotFoundException (subclasse d'IOException)
        // ...
        fr.close();
    }

    public static void main(String[] args) {
        try {
            llegir("dades.txt");
        } catch (IOException e) {
            System.out.println("No s'ha pogut llegir el fitxer: " + e.getMessage());
        }
    }
}

Amb throws, "delegues" la responsabilitat de capturar l'excepció cap amunt: cada mètode pot triar entre capturar-la ell mateix (amb try-catch) o tornar-la a declarar amb throws i deixar-la pujar un nivell més, fins que algú (típicament el main, o una capa superior de l'aplicació) la capturi definitivament.

Les excepcions unchecked (RuntimeException i subclasses) es poden llançar sense declarar-les amb throws; el compilador no ho exigeix. Tot i així, sovint és bona pràctica documentar-les igualment perquè qui usi el teu mètode sàpiga què esperar-se.

10. Excepcions personalitzades

Les excepcions que ofereix Java (IOException, IllegalArgumentException...) són genèriques. Quan volem expressar un error propi del domini de la nostra aplicació, podem crear la nostra pròpia classe d'excepció.

SaldoInsuficientException.java Java 
public class SaldoInsuficientException extends Exception {

    public SaldoInsuficientException(String missatge) {
        super(missatge); // reutilitza el constructor de Exception per guardar el missatge
    }
}
ComptaCorrent.java Java 
public class ComptaCorrent {
    private double saldo;

    public void retirar(double quantitat) throws SaldoInsuficientException {
        if (quantitat > saldo) {
            throw new SaldoInsuficientException(
                "No es pot retirar " + quantitat + " €: el saldo actual és de " + saldo + " €");
        }
        saldo -= quantitat;
    }
}
Ús.java Java 
ComptaCorrent compte = new ComptaCorrent();
try {
    compte.retirar(500);
} catch (SaldoInsuficientException e) {
    System.out.println("Operació rebutjada: " + e.getMessage());
}

Per decidir de quina classe heretar:

  • Hereta d'Exception si vols que sigui checked (el compilador obligarà a capturar-la o declarar-la): útil per a errors que qui crida el mètode ha de preveure sí o sí (com el saldo insuficient de l'exemple).
  • Hereta de RuntimeException si vols que sigui unchecked: útil per a errors de programació que no té sentit obligar a capturar arreu (per exemple, un identificador d'alumne negatiu que mai hauria de passar si la resta del codi és correcte).
NotaInvalidaException.java Java 
public class NotaInvalidaException extends RuntimeException {
    public NotaInvalidaException(String missatge) {
        super(missatge);
    }
}

11. Bones pràctiques

  • No deixis mai un catch buit. Capturar l'excepció i no fer-hi res (catch (Exception e) {}) amaga errors que després costen molt de trobar. Com a mínim, escriu-ho a un println o a un log.
  • Captura el tipus més específic possible, no sempre Exception en general. Si tractes tots els errors igual, perds la informació de què ha fallat realment.
  • No usis excepcions per controlar el flux normal del programa (per exemple, no llancis una excepció per sortir d'un bucle quan podries usar una condició normal). Les excepcions són per a situacions excepcionals, no habituals.
  • Allibera sempre els recursos: fitxers, connexions... Prefereix try-with-resources abans que un finally manual.
  • Escriu missatges d'error clars i útils, que diguin què ha passat i, si és possible, amb quines dades ("Fitxer no trobat: " + nomFitxer, no simplement "Error").
  • No converteixis un error en un altre sense guardar-ne l'origen. Si has d'embolicar una excepció dins d'una altra, passa-li la causa original: throw new MevaException("...", e); (constructor (String, Throwable)).
  • Documenta els throws dels teus mètodes (amb Javadoc @throws) perquè qui els faci servir sàpiga quins errors pot rebre.
